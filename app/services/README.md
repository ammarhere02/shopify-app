# app/services/ — business logic

## What this folder is
The rules of the app, kept out of the routes so they can be tested without HTTP. Five services matter most:

- **Tenant** (`shop.server.ts`): install, uninstall, and "is this shop allowed right now".
- **Sync** (`sync.server.ts`): copies the Shopify catalog into MySQL, page by page, safely repeatable.
- **Webhooks** (`webhook.server.ts`): one pipeline that records a receipt, drops duplicates and picks the status code.
- **Developer API** (`api.server.ts`, `api-key.server.ts`): API key authentication, rate limits (60/min per key, 5/min sync starts, 10/min generation starts), the error envelope.
- **Storefront badge** (`storefront-badge.server.ts`): the only code allowed to answer the public.

Files without `.server` in the name are pure functions with no database or network, which is why they have plain unit tests.

## How the sync works (`sync.server.ts`)
1. `startSyncRun`: `SELECT ... FOR UPDATE` on the shop row. A RUNNING run younger than 15 min → `SyncConflictError`; older → marked FAILED "Abandoned". Creates the `sync_runs` row.
2. Query `ShopIdentity`, save shop GID and name.
3. Loop pages of 25 products. Network calls happen OUTSIDE transactions. `completeVariants` fetches extra variant pages (100) and fails if the product's `updatedAt` changed meanwhile.
4. One transaction per page: `lockActiveRun` (rechecks shop installed + run still RUNNING) → upserts → counters + cursor.
5. Only after the last page: `markStaleProducts` (soft delete rows with `syncedAt` older than run start) + SUCCEEDED. A failed run never marks anything stale.
6. Any error → FAILED with message; committed pages stay. Re-run restarts from page one (cursor is diagnostic only). A thrown `Response` is rethrown after recording failure.

Bounds: 60s work budget checked between operations, 400 product pages, 100 variant pages per product, 30s per transaction.

## How a description generation works (`description-generation.server.ts`)
`deps` = `{ shopify: ShopifyClient, ai: OpenRouterClient, config: AiConfig }`, so tests pass fakes.

`runGeneration` makes two provider calls per job:
1. **Research** (`researchProduct`, skipped when `config.research` is off or `researchPlan` finds no vendor / model token): `ai.generate` with `RESEARCH_JSON_SCHEMA`, `buildResearchMessages` (with the selected images) and `webSearch: { maxUses: AI_RESEARCH_MAX_SEARCHES, maxResults: AI_RESEARCH_MAX_RESULTS }`, output budget 3000 tokens (room for 12 facts with URLs plus hidden reasoning tokens; 1000 cut off spec-heavy products). The answer goes through `validateResearchOutput` with the citations the client extracted. Never fatal: a provider error becomes a `FAILED` record whose reason carries the provider error's exact message (e.g. `INVALID_OUTPUT: The model returned an empty answer (finish reason: tool_calls, …)`), anything doubtful an `UNCERTAIN` one, and the job continues.
2. **Description**: `buildDescriptionMessages({ …, researchFacts: research.facts })`, so only confirmed facts reach the prompt; `trustedText` includes them, so a specification taken from research is not flagged as an unsupported claim.
The job stores `validatedJson = { …description, research }` (no migration: the record lives inside the existing JSON column; older rows have no `research` key and read as `null`), usage/cost/latency summed over both calls, the description call's generation id, and the research `reason` among the warnings when the status is `UNCERTAIN` or `FAILED`. Research is not part of the input hash and does not change job states, idempotency or the limits: one job = one daily-limit count, whatever it searched.
1. Validate the request: idempotency key format, 1–`maxImages` distinct `gid://shopify/MediaImage/<n>` ids (a URL can never be passed), context ≤ 2000, model in the allowlist. Nothing is fetched or stored for a bad request.
2. A known `(shopId, idempotencyKey)` returns its job at once: no Shopify call, no model call, never rate-limited.
3. Local product lookup by `shopId` (another shop's product = NOT_FOUND before any network call), then a live Shopify read (`PRODUCT_FOR_DESCRIPTION_QUERY`). Every selected id must be a READY image of that product.
4. Snapshot (trusted fields, current `descriptionHtml`, its SHA-256, Shopify `updatedAt`, chosen images) and input hash.
5. One transaction with `SELECT ... FOR UPDATE` on the shop row: re-check the key, fail abandoned jobs, enforce `maxConcurrentPerShop` and `dailyLimitPerShop` (rolling 24h, failed attempts count), create job + input. Two simultaneous clicks cannot both pass.
6. Returns `{ job, created, run }`. The caller starts `run()` without awaiting and answers 202 (same pattern as the sync). With `enqueueOnly` (batches) no `run` is returned and the concurrency check is skipped: the worker runs the job later, rebuilding the prompt from the stored input with `prepareFromJob`.
7. `runGeneration` never throws. QUEUED → RUNNING (if it cannot, the job was abandoned meanwhile and nothing runs) → model call → `validateModelOutput` → claim warnings → `completeJob`. Invalid output → FAILED `INVALID_OUTPUT: <reason>. Model said: <300-char sample>`, not retried. Provider errors → FAILED `<KIND>: <message>`. Anything else → FAILED `INTERNAL: Unexpected error while generating` (details only in the log).

## How webhooks work (`webhook.server.ts`)
Input is always the verified result of `authenticate.webhook` (the route does that first).
1. `processWebhook`: look up the shop by the verified domain → `claimReceipt` (INSERT `RECEIVED`; unique `webhookId`). Duplicate → log + 200, handler never runs.
2. `requireActiveShop: true` and shop unknown/uninstalled → receipt `PROCESSED` with note "ignored: shop not active", 200.
3. Handler runs and calls `finish(tx, note?)`, which marks the receipt `PROCESSED` inside the handler's transaction. A deliberate skip is `PROCESSED` with a note in `error`.
4. Handler throws → receipt `FAILED` (message cut to 1000 chars, never the payload) → `logger.error` → **500** so Shopify retries with the same `webhookId`; a `FAILED` receipt may be claimed again.

`handleProductUpdate` (used by both `products/create` and `products/update`): the payload supplies only the product id and `updated_at`. Cheap skip if the event is older than our `updatedAtShopify` → otherwise re-fetch with `PRODUCT_BY_ID_QUERY` (client: 1 attempt, 3s timeout, 4s budget, because Shopify fails a delivery after 5s) → `product: null` = skip → `completeVariants` → `mapProductNode` → transaction { `upsertProductIfNewer`; finish }. Unknown local product is created. No offline session → throws → `FAILED` + 500.

`handleProductDelete`: payload is `{ id }` → GID → transaction { `softDeleteProductByGid`; finish }. 0 rows matched is a normal no-op.

Limits: processing is synchronous inside the request; there is no queue or replay. If all of Shopify's retries fail the receipt stays `FAILED` and Reconcile repairs the data. The full sync does not use the newer-than guard, so a sync page fetched before a webhook commit can briefly write the older copy; the next event or Reconcile corrects it.

## How the developer API works (`api.server.ts`)
`withApiAuth(request, { methods, bucket }, handler)`:
1. New `requestId` (also sent as `X-Request-Id`). Wrong method → 405.
2. IP already has 20 failed logins this minute → 429.
3. `Authorization: Bearer <key>` → hash → `developer_api_keys` row with its shop. Missing, malformed, unknown, revoked, or shop uninstalled → the SAME 401 body + `WWW-Authenticate: Bearer`; the real reason is only logged as `authFailure`.
4. Per-key limit keyed by the key's DB id: 60/min, or 5/min for the `sync` bucket → 429 + `Retry-After`.
5. `lastUsedAt` is written only if older than 60s.
6. Handler gets `{ shop, requestId, request }`. `ApiError` → `{ error: { code, message, details?, requestId } }`; any other exception → 500 `internal_error` with no internals.
7. One `api.request` log line: requestId, method, route, shopId, keyId, status, durationMs. Never the key or the Authorization header.

`internalNote` IS returned by this API (the key belongs to the merchant). `serializeEnrichment` must never be used for the storefront endpoint.

Limits: rate limits live in memory (reset on restart, per process). The 202 sync has no durable worker: a restart leaves the run RUNNING and POST /syncs answers 409 until the 15-minute abandon rule.

## Rules
- The sync never writes `product_enrichments`.
- Services take `shopId` as a parameter; they never read it from a request.

## How a description reaches Shopify (`description-apply.server.ts`)

Apply and Restore share one `writeDescription`:
1. `hasScope(shop.scopes, "write_products")` else `FORBIDDEN` (403).
2. Sanitize again; refuse empty or over 10,000 characters.
3. Live read. Apply only: the current description's SHA-256 must equal the snapshot hash, or equal the hash of the text being written (our own interrupted write); otherwise `STALE` (409). Restore skips this: the merchant chose an old text on purpose.
4. `productUpdate` with `id` + `descriptionHtml`, outside any DB transaction. Transport/GraphQL errors are thrown by the client; `userErrors` become `REJECTED` (422) keyed by field.
5. One transaction: version row (before = live text, after = mutation response, Shopify `updatedAt`), job `APPLYING → APPLIED`, `products.updatedAtShopify` refreshed.

Apply first runs `recoverAbandonedApplies` (APPLYING older than 2 min → APPROVED with a note), then moves `APPROVED → APPLYING` as a conditional update (one winner of two clicks). A refusal at 3 or 4 returns the job to APPROVED with the reason, so Apply can be retried.
