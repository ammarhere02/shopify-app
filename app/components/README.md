# app/components/ — React components used by pages

## What this folder is
UI that is too large to live inside a route file. Components here are client code: they may import pure modules (no `.server` in the name) and types, never repositories, `db.server` or anything that reads the environment.

| File | Used by | Behaviour |
|---|---|---|
| `AiDescriptionSection.tsx` | `routes/app.products.$id.tsx` | The AI description workflow for one product, rendered as a fragment of `s-section`s that the product page places in its main column. Talks only to the resource route `/app/products/:id/generation`. **1. Generate**: thumbnail grid (selected = strong border + subdued background, "n of max selected"), optional facts (max 2,000), model select when more than one is allowed, primary Generate (or Regenerate + Generate new once a job exists). One idempotency key per intended generation: kept across a failed submit, replaced after a successful one, so a retried click cannot create a second billable job. While the job is QUEUED or RUNNING it loads `?jobId=` every 2 s and stops when the job is finished; a poll is a plain read; inputs are disabled meanwhile. **2. Review**: status and review badges (+ "Edited" when the text differs from the generated one), model, tokens, latency, cost, warnings banner, failure banner with the stored error, HTML textarea next to a live preview (side by side above 720px, stacked below), SEO suggestions (shown only, never written), Approve / Save draft / Reject / Reset to generated text, Edit again after approval. **3. Write to Shopify** (APPROVED/APPLYING/APPLIED): a warning when the shop has not granted `write_products` (`canWrite`), "Apply to product…" opens an `s-modal` showing the last recorded text next to the new one before `intent=apply`; a STALE result shows its own banner; an APPROVED job with an `error` shows the last refusal. **Sales channels** (`canPublish`): "Publish to a channel…" loads `?publications=1` into a modal with a select (already-published channels are marked) and a warning when the product is not ACTIVE; `intent=publish`. **Descriptions written by this app**: table, newest first with a Current badge; Restore on older rows and "Restore what it replaced" on the newest (the text before the first apply), each through a confirmation modal showing the text, then `intent=restore` with `versionId` + `which`. **Generation history**: table of the last 10 generations with a View action |
## Rules
- The preview renders `sanitizeHtml(draft)` from `services/html-sanitize.ts`, the same function the server applies before storing. Never pass unsanitized text to `dangerouslySetInnerHTML`.
- No secret reaches this folder. The loader sends model names and limits only.
- Polaris web components (`s-*`) need no import; props are camelCase and typed by `@shopify/polaris-types`.
- The merchant's edits survive background requests: the editor text is replaced only when a different job arrives (generate, regenerate, View from history, a finished poll) or a restore answers. Save draft and Approve answers never overwrite what was typed after the click. The preview is `useMemo(sanitizeHtml(draft))`: it updates on every keystroke without a request or loader.
- Feedback: only the clicked button shows `loading` (the pending `intent` read from `actions.formData`), every other action is disabled until the answer arrives; success is a toast, errors are banners placed in the step they belong to (generate errors in step 1, everything else in step 2, STALE in step 3).
- Approving does not write to Shopify. Applying, publishing and restoring each open a confirmation modal (`s-modal` + `commandFor`/`command="--show"`) and only then submit; the server re-checks state, scope and staleness.
