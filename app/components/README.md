# app/components/ — React components used by pages

## What this folder is
UI that is too large to live inside a route file. Components here are client code: they may import pure modules (no `.server` in the name) and types, never repositories, `db.server` or anything that reads the environment.

| File | Used by | Behaviour |
|---|---|---|
| `AiDescriptionSection.tsx` | `routes/app.products.$id.tsx` | The AI description workspace for one product: a two-column `s-grid` inside an `s-query-container` (280px + rest above 760px of page width, stacked below). Talks only to the resource route `/app/products/:id/generation`. **Left column**: Generate card (uniform 84px thumbnails with a strong border when selected, "n of max selected", facts (max 2,000), model select when more than one is allowed, Generate description / Generate new), then the page's `asideTop` (badge editor), Sales channels (Publish stays separate from Apply and says so), then `asideBottom` (product details). One idempotency key per intended generation: kept across a failed submit, replaced after a successful one, so a retried click cannot create a second billable job. **Right column** (wrapped in `s-query-container`, so its grids measure the workspace itself): the Description card with one main status badge (`aiStatusLabel`: Generating states, Draft, Approved, Applying, Applied, Rejected, Failed) plus an "Unsaved edits" badge, a compact action bar whose primary button follows the state (Approve → Apply to product… → Regenerate; Save draft, Edit again, Reject and Regenerate as secondary/tertiary), banners (errors, STALE, missing scope, failed, applied, warnings), then a WAI-ARIA tab strip **Description** (formatted, default) / **Edit HTML** (textarea beside the live preview above 720px of workspace width, stacked below; Reset to generated text) / **SEO suggestions** (never written), and a collapsed **Generation details** row (model, prompt version, tokens, latency, cost, provider id, created). While QUEUED/RUNNING it loads `?jobId=` every 2 s (plain read) and shows a spinner; inputs are disabled. **History card**: tabs **Generations** (last 10, View opens one) and **Written to Shopify** (versions, Current badge, Restore / Restore what it replaced through a confirmation modal showing the text, then `intent=restore` with `versionId` + `which`). Apply opens an `s-modal` showing the last recorded text next to the new one before `intent=apply` |
## Rules
- The preview renders `sanitizeHtml(draft)` from `services/html-sanitize.ts`, the same function the server applies before storing. Never pass unsanitized text to `dangerouslySetInnerHTML`.
- No secret reaches this folder. The loader sends model names and limits only.
- Polaris web components (`s-*`) need no import; props are camelCase and typed by `@shopify/polaris-types`.
- Motion is limited to real state: a shimmer skeleton while a job is QUEUED/RUNNING, a fade-in when a tab panel appears, and a short highlight on the preview plus an "Updating" dot while the merchant types (cleared 700 ms after the last keystroke; a word count otherwise). All of it is disabled under `prefers-reduced-motion`. No fake progress or streaming.
- Tabs are the only custom markup: `role=tablist/tab/tabpanel`, arrow keys, Home/End, roving tabindex, styled by a scoped `<style>` (`eh-` classes). Tab selection and the collapsed/open state live in component state that no poll or action answer touches.
- The merchant's edits survive background requests: the editor text is replaced only when a different job arrives (generate, regenerate, View from history, a finished poll) or a restore answers. Save draft and Approve answers never overwrite what was typed after the click. The preview is `useMemo(sanitizeHtml(draft))`: it updates on every keystroke without a request or loader.
- Feedback: only the clicked button shows `loading` (the pending `intent` read from `actions.formData`), every other action is disabled until the answer arrives; success is a toast, errors are banners placed in the step they belong to (generate errors in step 1, everything else in step 2, STALE in step 3).
- Approving does not write to Shopify. Applying, publishing and restoring each open a confirmation modal (`s-modal` + `commandFor`/`command="--show"`) and only then submit; the server re-checks state, scope and staleness.
