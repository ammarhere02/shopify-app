# app/components/ — React components used by pages

## What this folder is
UI that is too large to live inside a route file. Components here are client code: they may import pure modules (no `.server` in the name) and types, never repositories, `db.server` or anything that reads the environment.

| File | Used by | Behaviour |
|---|---|---|
| `Notice.tsx` | the three admin pages | `useNotice()` → `{ notice, show(tone, message), clear }` and `<Notice notice onDismiss>`: ONE result banner at the top of the page. Success fades out after `NOTICE_MS` (5 s); critical/warning stay until closed or replaced. Every finished action (badge save/remove, generate, save draft, approve, reject, apply, restore, publish, batch queue, sync) reports here through `show` (the AI workspace gets it as `onNotice`). No toasts |
| `AiDescriptionSection.tsx` | `routes/app.products.$id.tsx` | The product workspace: two columns from 760px of page width, one below. The admin iframe grows with its content, so there is no viewport-height fitting: the Description body (max 560px) and the History body (max 260px) scroll inside their panels instead. Talks only to the resource route `/app/products/:id/generation`. **Left panel** (300px): hero image (last selected image, `object-fit: contain` on a light background so tall products are not cropped), a thumbnail strip of toggle buttons (`aria-pressed`, tick when selected, disabled at `maxImages`), the page's status badges, then collapsible sections (`Collapse`: real buttons with `aria-expanded`, chevron): **Generate** (facts, model, Generate description / Generate new draft), **Storefront badge** (the page's editor, passed as `badgeEditor`, hint = badge text). Everything under the hero (badges, sections) sits in one scroll area capped at 560px, so the card keeps a fixed height and scrolls as one unit. One idempotency key per intended generation: kept across a failed submit, replaced after a successful one. **Right column**: the **Description panel** with a header (title, one main status badge from `aiStatusLabel`, "Unsaved edits", the state-driven action bar: Reject / Regenerate / Save draft / Approve → Regenerate / Edit again / Apply to product… → Regenerate), a tab strip **Description** / **Edit HTML** / **SEO suggestions**, and a scrolling body (stale / missing-scope / failed / claim-warning banners, empty state, shimmer skeleton while QUEUED/RUNNING with a 2 s poll, the formatted text, the editor beside its live preview from 720px of panel width, a collapsed Generation details grid). Both columns stretch to the taller one (the Description body absorbs the difference and scrolls), so there is no empty corner. Below it the **History panel** (body scrolls past 240px) with tabs **Generations** (View opens one) and **Written to Shopify** (versions, Current badge, Restore / Restore what it replaced through a confirmation modal, then `intent=restore`). Then the **Product panel**: Sales channels (Publish, separate from Apply and explained as such) beside Product details (the page's `productDetails`), body scrolls past 280px. Apply opens an `s-modal` showing the last recorded text next to the new one before `intent=apply`. Results go to the page's `onNotice` |
## Rules
- The preview renders `sanitizeHtml(draft)` from `services/html-sanitize.ts`, the same function the server applies before storing. Never pass unsanitized text to `dangerouslySetInnerHTML`.
- No secret reaches this folder. The loader sends model names and limits only.
- Polaris web components (`s-*`) need no import; props are camelCase and typed by `@shopify/polaris-types`.
- Motion is limited to real state: a shimmer skeleton while a job is QUEUED/RUNNING, a fade-in when a tab panel appears, and a short highlight on the preview plus an "Updating" dot while the merchant types (cleared 700 ms after the last keystroke; a word count otherwise). All of it is disabled under `prefers-reduced-motion`. No fake progress or streaming.
- Tabs are the only custom markup: `role=tablist/tab/tabpanel`, arrow keys, Home/End, roving tabindex, styled by a scoped `<style>` (`eh-` classes). Tab selection and the collapsed/open state live in component state that no poll or action answer touches.
- The merchant's edits survive background requests: the editor text is replaced only when a different job arrives (generate, regenerate, View from history, a finished poll) or a restore answers. Save draft and Approve answers never overwrite what was typed after the click. The preview is `useMemo(sanitizeHtml(draft))`: it updates on every keystroke without a request or loader.
- Feedback: only the clicked button shows `loading` (the pending `intent` read from `actions.formData`), every other action is disabled until the answer arrives; the result message goes to the page-level `Notice` at the top (success fades, errors stay). Banners inside the workspace are reserved for state that needs reading: STALE, missing scope, a failed job, claim warnings.
- Approving does not write to Shopify. Applying, publishing and restoring each open a confirmation modal (`s-modal` + `commandFor`/`command="--show"`) and only then submit; the server re-checks state, scope and staleness.
